# PKFM31 controlled hardware trial — plan, 21 October 2026

**Status: plan only. Nothing has been packaged, copied or flashed.** Each
preparation step below produces local files only; flashing needs the user's
go-ahead at the session itself.

## Question

Is the frozen emulator budget (158.21 µs steady mean, plus six other
ceilings; [EMULATOR_BUDGET.md](EMULATOR_BUDGET.md)) the real hardware limit
for PKFM31, or a conservative one? The trial measures, on the Octatrack MKII,
the real per-frame audio-ISR time of a ladder of PKFM31 workloads whose
modelled cost runs from well inside the budget (123.6 µs) to the worst row
(186.9 µs), and finds the highest rung that runs cleanly.

**Why a ladder, not just the worst row.** The emulator puts PKH4O2's failing
two-ColdFire shape at 157–167 µs, and that shape became sluggish and locked
up on hardware; its `.PRF` captures read about 288–331 µs mean with deadline
misses ([hardware record](CF_FOOTPRINT_20261016_HARDWARE.json)). PKFM31's
worst rows model higher than that, so they may fail too. Climbing from the
bottom gives a usable answer even if the top fails, and stops before a
lockup.

**Prediction, registered before the trial (inferred).** PKH4O2's captures
imply a hardware/model ratio of about 1.7–2.1 (288–331 µs against 157–167 µs
modelled; the captures came from a degrading run, so the range is rough). At
that ratio, rung R2 (154.0 µs model) lands near 260–320 µs on hardware,
straddling the 80% line (290.2 µs of the 362.8 µs period), and the worst rung
(186.9) lands near 320–390 µs, close to or over the deadline. The budget
would then be real. A clearly lower ratio, with the top rungs clean, would
show it is conservative for this code.

## What gets measured

PKFM31 keeps the hybrid hardware profiler on by default. Every STOP writes a
new `/PKH2nnnn.PRF` to the card root (never overwriting one), stamped with
PKFM31's source id `0657c9d03197712016cf2bca041d059539a2a0baa56a8c2bed6882b473727f58`.
`tools/perky/read_hybrid_profile.py` decodes it: full-frame mean and maximum
from the 132 MHz DMA timer, a 64-bin full-frame histogram (1,024 ticks per
bin), hard deadline misses, 80%-margin overruns, ColdFire control, render and
pack split, DSP wait loops, frame count and active voice mask.

Each rung's project is also run in the emulator with the same profiler
structure dumped from emulated RAM, so the hardware and model numbers come
from **the same code and the same timing window**. The per-rung ratio
(hardware ÷ model) is the main result.

## The ladder

Each rung is its own project in one trial set, generated by the same fixture
tools as the qualification rows: WT V1, WT V2 (modes 1, 2), V3 and V4 as
listed, stock STATIC tone on T3/T4/T7/T8, all fourteen FX, 120 BPM, 64 steps,
dense locks. A voice that is "off" has no PERKY signature on its track, so it
takes the stock path. Model figures are the steady means measured on the
same image ([structural study](STRUCTURAL_PLACEMENT_STUDY.md) and
[campaign rows](ORCHESTRATION_CF_QUALIFICATION.md)). The twins rerun them on
the actual trial projects, where off voices take the stock path, so the
figures may shift a little.

| Rung | PERKY voices placed | Model mean (µs) | Model vs budget |
|---|---|---:|---|
| R0 | none (pipeline check) | 123.6 | inside |
| R1 | V4 metallic Hat (DSP-A) | 140.0 | inside |
| R2 | V2 WT + V3 Slap | 154.0 | inside: all seven ceilings pass |
| R3 | V3 Slap + V4 Hat | 159.5 | just over |
| R4 | V1 WT + V2 WT + V3 Slap | 163.0 | over |
| R5 | V2 WT + V3 Slap + V4 Hat | 170.5 | over |
| R6 | all four: WT, WT, Slap, Hat | 179.4 | over |
| R7 | all four: WT, WT, Resonant Snare/Bass MODE locks, Noise/Tone | 183.9 | over |
| R8 | all four: WT, WT, Slap, Noise/Tone (worst) | 186.9 | over |

R7 is included because Resonant is the family the user has found heaviest on
hardware.

## Preparation (local, before the session)

1. **Package PKFM31** with the existing wrapper tool, which round-trips both
   wrappers back to the MAIN image, checks the card size limit
   (1,048,588 bytes) and confirms a corrupted card file is rejected:

   ```sh
   PERKY_FULL_MAP_WORK=out/perky/hybrid/full-map-kernels-v8 \
   PERKY_EFT="$PWD/out/eft-qualified/elektron-firmware-tool" \
     .venv/bin/python tools/perky/wrap_perky_full_map.py
   ```

   Output: `out/perky/hybrid/full-map-kernels-v8/upgrade/OCTATRACK_PKFM31.bin`
   (card) and `OCTATRACK_OS1.40C_PKFM31.syx` (MIDI), recorded in
   `WRAPPERS.json`. MAIN SHA256 `77c70410…6982a9`.
2. **Build the trial set**: the nine rung projects plus `PERKYAH.DAT`,
   exported as a card folder tree with `SHA256SUMS` and a manifest. This
   needs a small fixture adapter that writes PERKY signatures only on each
   rung's placed voices.
3. **Run the nine model twins** (32,768 blocks each) on exactly those
   projects, with the profiler structure dumped and decoded, and store them
   beside the trial set.
4. **Write `TRIAL.json`**: image, ELF and wrapper hashes, the profile source
   id, the set manifest and the twins, so the decoder can bind each `.PRF` to
   PKFM31.
5. **Check the rollback kit** against its records:

   | File | SHA256 |
   |---|---|
   | `out/frozen/PERKY4S/OCTATRACK_PERKY4S.bin` (card) | `bc9367ec56b2f310f733d0808a88e74e44da32b63f9483468af09760f7ac8fa9` |
   | `out/frozen/PERKY4S/OCTATRACK_OS1.40C_PERKY4S.syx` (MIDI) | `922a7097062012f9a8738e6306f8a946bb4a7bc03ae37b2b4a8b9c1447d2bb1d` |
   | `downloads/extracted/OCTATRACK_OS1.40C.syx` (stock, last resort) | `0a8d2d2b35c2cc78fa338576adc1af0cbc094cef973255103165c73edd87f2b6` |

   Also have a DIN MIDI interface and `make midi-flash` (or a SysEx app)
   ready before flashing anything.

## Session (on the unit, with the user's go-ahead)

**Before.**
- Write down the installed OS (SYSTEM STATUS → OS VERSION).
- Use a separate CF card for the trial, or back up the user's card in full
  first ([BUILDING.md §4](../../../docs/guide/BUILDING.md)). Never load the
  user's own projects under PKFM31.
- Copy the trial set and `PERKYAH.DAT` to that card.
- Make a throwaway trial project the active one, because OS UPGRADE syncs the
  active project to the card first.

**Flash.**
1. Copy `OCTATRACK_PKFM31.bin` to the card root and eject on the computer.
2. On the unit: PROJECT → SYSTEM → OS UPGRADE → YES ([BUILDING.md §5](../../../docs/guide/BUILDING.md)).
3. When it restarts, power-cycle once more before judging anything; first
   boots after an upgrade can play garbled audio
   ([failure register](../../../docs/contributing/FAILURE_MODES.md)).
4. Confirm that OS VERSION reads PKFM31.

**Each rung.**
1. Load the rung's project and PLAY.
2. At 30 s, do one fixed UI action and note how fast it responds: turn
   track 3's LEVEL encoder ten detents, then press T3's trig key. Filming
   the screen gives an objective lag measure.
3. At 60 s, STOP. A new `.PRF` is written. Record the rung, start and stop
   time, OS tag, `.PRF` name, what was heard and the UI response.
4. Optionally, record MAIN OUT into a computer for each rung, so dropouts and
   clicks can be checked afterwards.
5. Before climbing, decode the `.PRF` in USB DISK MODE.

**Go to the next rung** only if all of these hold:
- zero hard deadline misses;
- no audible glitch;
- the UI responds normally;
- the STATIC tracks keep streaming.

**Stop climbing at the first rung that fails any of them.** STOP as soon as
degradation is noticed, so the `.PRF` is written before a lockup could
prevent it. Do not drive a rung into a lockup to confirm it; PKH4O2 already
showed that failure. If the unit locks up anyway: note the time and the last
responsive action, power-cycle, and record the event.

**Extend.**
- Rerun the highest clean rung for 2 minutes.
- If R8 (or the highest clean rung) stays clean, soak it for 10 minutes.
- On the soaked rung, run one `.PRF` per action: STOP/START, Part change,
  Bank change, project reload, and a scene/fader sweep.

**Roll back.**
1. Copy `OCTATRACK_PERKY4S.bin` to the card root, then OS UPGRADE.
2. Power-cycle and confirm that OS VERSION reads PERKY4S.
3. Play a known PERKY4S project briefly (T1/T5) to confirm it works.
4. If the unit does not boot: hold FUNC at power-on (Startup Menu) → TRIG 3
   MIDI UPGRADE, and send the PERKY4S `.syx` (or stock 1.40C) at DIN rate
   ([BUILDING.md §7](../../../docs/guide/BUILDING.md)). The Startup Menu is in
   flash that an OS upgrade never writes.

## Reading the result

| Outcome | Meaning |
|---|---|
| Misses or UI/audio degradation first appear around R3–R5, and the hardware/model ratio is close to PKH4O2's | The budget is the real limit: about two heavy ColdFire voices. The decisions in the structural study stand. |
| R8 runs the 10-minute soak and the lifecycle actions with zero hard misses, a full-frame mean ≤ 290 µs and normal UI and audio | The budget is conservative for PKFM31. The highest clean rung, in model terms, becomes the evidence for a separately documented budget revision, which is the user's decision. The frozen budget file is not changed by the trial. |
| Somewhere in between | The highest clean rung and the per-rung ratios define an empirical ceiling for this image and workload only. |

The ratio's trend across rungs also matters. A ratio that is flat as load
grows means the model is simply scaled. A ratio that grows with load points
to costs the model does not see (cache, SDRAM, card or DMA contention). The
trial cannot tell those apart.

## Limits

- One unit, one card and one workload family. A clean rung qualifies that
  rung, not every selection or control history.
- `.PRF` export happens only on STOP, so it cannot capture the state after a
  total lockup.
- The profile shares its source id across a build. It cannot authenticate
  the installed wrapper, so record the visible OS tag separately.
- Hardware audio is checked by ear and optional recording, not bit for bit;
  exactness remains the emulator gates' job.
- PKFM31 is not a release. Passing this trial does not admit it; packaging,
  versioned project and asset delivery, and an acceptance pass remain
  ([handoff](CLAUDE_HANDOFF.md), "What completion still requires").
